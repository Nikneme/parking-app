# Регламент обновления и отката

## 1. Правило источника истины

Единственным источником production-кода является Git-репозиторий. Любые изменения должны быть:

1. внесены в рабочую ветку;
2. проверены локально;
3. закоммичены;
4. согласованы с Заказчиком;
5. выложены через стандартный deploy-процесс.

Ручные правки в production без фиксации в репозитории запрещены.

## 2. Подготовка изменения

```bash
git checkout -b change/<short-name>
npm install
npm run smoke:runtime
npm run ops:inventory
git status
```

Перед merge проверьте:

- нет секретов в Git;
- нет `data/`, backup, дампов, `.env`, `.DS_Store`;
- изменены только ожидаемые файлы;
- обновлена документация, если меняются эксплуатационные правила.

## 3. Выкладка новой версии

1. Создать backup БД:

```bash
npm run db:backup
```

2. Зафиксировать commit/tag:

```bash
git tag release-YYYYMMDD-N
git push --tags
```

3. Выполнить deploy через Railway/GitHub/Yandex pipeline.
4. Проверить `/health`.
5. Проверить login, dashboard, открытие тестового устройства, logs и audit.
6. Зафиксировать результат в отчёте приёмки.

## 4. Откат к предыдущей версии

1. Остановить выкладку или выбрать предыдущий deployment в платформе.
2. Если использовались миграции с необратимыми изменениями, восстановить БД из backup:

```bash
CONFIRM_RESTORE=YES npm run db:restore -- ./backups/<backup>.dump
```

3. Проверить `/health`.
4. Проверить критичные сценарии.
5. Зафиксировать причину отката, версию и ответственного.

## 5. Требования к отчётности

Каждое обновление фиксируется письменно:

- дата и время;
- версия/commit/tag;
- кто выполнял;
- что изменено;
- был ли backup;
- результат smoke-проверки;
- замечания и откаты.
