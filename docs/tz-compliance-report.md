# Отчёт о выполнении ТЗ по передаче, безопасности и эксплуатации

Дата подготовки: 2026-05-11
Проект: «Моя парковка»

## 1. Область выполнения

В пакет включены изменения приложения и эксплуатационные материалы для закрытия требований:

- Этап 1: передача под фактический контроль Заказчика.
- Этап 2: обязательные меры по безопасности.
- Этап 3: эксплуатационная упаковка и документация.
- Этап 4: регламенты эксплуатации.
- Этап 5: перечень внешних зависимостей и инвентаризация.
- Этап 6: приёмка выполнения.

Фактическая передача доступов к Yandex Cloud, домену, DNS, почтовому ящику, сертификатам, репозиторию и БД требует действий владельца этих ресурсов вне кода приложения. Для этого в пакете подготовлены реестры, чек-листы, инструкции и шаблоны актов.

## 2. Выполненные изменения в коде

### 2.1. Пользовательские PIN и пароли

- PIN/пароли пользователей хранятся как scrypt-хэши формата `pin:v1:scrypt:<salt>:<hash>`.
- Легаси-PIN в открытом виде при успешном входе автоматически мигрирует в хэш.
- Новые пользователи, сбросы и bootstrap-admin сохраняют только хэш.
- Сравнение текущих открытых значений выполняется только для безопасной миграции и через timing-safe сравнение.

### 2.2. Стартовые доступы

- Действующий PIN/пароль не отправляется по email.
- В email остаётся только логин и указание получить стартовый пароль у администратора.
- Новый/сброшенный пароль помечается как временный.
- До смены временного пароля пользователь перенаправляется на `/change-password`.
- Срок действия стартового пароля задаётся `START_PIN_TTL_HOURS`.

### 2.3. Защита от перебора

- Реализовано ограничение попыток входа по связке `IP + телефон`.
- Реализованы отдельные лимиты по IP и по телефону.
- Серии неудачных попыток временно блокируются.
- Неудачные и заблокированные попытки пишутся в audit-журнал.

### 2.4. CSRF

- Все POST/PUT/PATCH/DELETE требуют `_csrf` или `X-CSRF-Token`.
- Токен добавлен в формы login, logout, смены пароля, управления пользователями, зонами, устройствами и журналами.
- Проверка CSRF включена в runtime smoke-тест.

### 2.5. Публичные директории

- Закрыты `/data`, `/public/data`, `/.git`, `/__MACOSX`.
- Static-раздача настроена с `dotfiles: deny`, `index: false`, `redirect: false`.
- Production-архив собирается без `.git`, `node_modules`, локальных данных, временных архивов и backup-файлов.

### 2.6. Учётные данные устройств и интеграций

- Пароли устройств выносятся из URL в отдельное поле.
- Пароли устройств шифруются `AES-256-GCM`.
- Ключ шифрования задаётся через `DEVICE_SECRET_ENCRYPTION_KEY`.
- В production запуск запрещён без собственного `DEVICE_SECRET_ENCRYPTION_KEY`.
- Передача паролей устройств в gateway запрещена в production.

### 2.7. Тестовые и демонстрационные артефакты

- Reference-устройства больше не создаются автоматически в production.
- `DEV_MEMORY_DB=true` запрещён в production.
- Скрипты `mock-gateway` и `emulate-scenarios` заблокированы в production без явного `ALLOW_DEMO_ARTIFACTS=true`.
- Демо-пользователи создаются только в локальном `DEV_MEMORY_DB` режиме.

### 2.8. Администраторы и критичные доступы

- Bootstrap-admin создаётся только из `ADMIN_PHONE` и `ADMIN_PIN`.
- Хардкод постоянного дефолтного администратора отсутствует.
- Bootstrap-admin обязан сменить стартовый пароль при первом входе.
- Подготовлен реестр административных и сервисных доступов: `docs/inventory-and-handover.md`.

### 2.9. Базовый hardening

- Включены secure/session cookie-настройки.
- Добавлены security headers: `X-Content-Type-Options`, `X-Frame-Options`, `Cross-Origin-Opener-Policy`, `Content-Security-Policy`, `Referrer-Policy`, `Permissions-Policy`, HSTS в production.
- Добавлен `/health` для проверки доступности БД.
- Инициализация БД в production не игнорирует ошибки без явного `ALLOW_DB_INIT_FAILURE=true`.

## 3. Эксплуатационная упаковка

Добавлены документы:

- `docs/deployment.md` — развёртывание с нуля.
- `docs/update-rollback.md` — обновление, выкладка и откат.
- `docs/backup-recovery.md` — резервное копирование и восстановление.
- `docs/operations-regulations.md` — регламенты эксплуатации.
- `docs/inventory-and-handover.md` — инвентаризация и передача контроля.
- `docs/acceptance-act-template.md` — шаблон финальной приёмки.
- `docs/tz-compliance-report.md` — настоящий отчёт.

Добавлены эксплуатационные скрипты:

- `npm run ops:inventory` — формирует `reports/ops-inventory.json`.
- `npm run db:backup` — создаёт PostgreSQL backup через `pg_dump`.
- `npm run db:restore -- <backup.dump>` — восстанавливает backup через `pg_restore` после `CONFIRM_RESTORE=YES`.

## 4. Что должно быть передано вне архива

Следующие материалы не могут быть созданы внутри приложения и должны быть переданы фактическим владельцем инфраструктуры:

- доступ к репозиторию и production-ветке;
- доступ к Yandex Cloud, VM, контейнерам, unit-файлам и сервисам;
- доступ к домену `moyaparkovka.ru`, DNS, SSL и почте `mmoyaparkovka@yandex.ru`;
- актуальный backup production-БД;
- актуальные production env-переменные без раскрытия секретов в репозитории;
- перечень текущих суперпользователей и сервисных пользователей;
- подтверждение ротации паролей и ключей после передачи.

## 5. Проверка

Минимальная проверка после деплоя:

```bash
npm install
npm run smoke:runtime
npm run ops:inventory
```

Для production-проверки дополнительно:

```bash
curl -fsS https://moyaparkovka.ru/health
curl -I https://moyaparkovka.ru/data/users.json
```

Ожидаемо:

- `/health` возвращает `{"ok":true}`;
- `/data/users.json` возвращает 404;
- вход со стартовым паролем ведёт на смену пароля;
- POST без CSRF возвращает 403;
- opening устройства фиксируется в журнале;
- audit фиксирует входы, сбросы, изменения и подозрительные попытки.

## 6. Остаточные организационные действия

Для финального закрытия ТЗ Заказчик и Исполнитель должны заполнить и подписать:

- реестр передачи контроля в `docs/inventory-and-handover.md`;
- акт/отчёт приёмки в `docs/acceptance-act-template.md`;
- подтверждение ротации критичных доступов после передачи.
