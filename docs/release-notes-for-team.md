# Моя парковка: что изменилось в рабочей версии

Документ для команды, которая будет принимать текущую рабочую версию приложения вместо архивной версии.

## Главное

Текущая версия сохраняет базовый стек архивной версии: Node.js, Express, EJS, PostgreSQL. При этом она закрывает несколько эксплуатационных рисков и добавляет сценарии, которых не было в архиве.

Ключевые улучшения:
- пароли пользователей хранятся как `scrypt`-хеши, старые открытые PIN перехешируются после успешного входа;
- включена CSRF-защита для POST-запросов;
- добавлен лимит попыток входа;
- закрыта выдача `/data` и `/public/data`;
- приложение не стартует в "полуживом" состоянии без базы, если не включен явный `DEV_MEMORY_DB=true`;
- сессии могут храниться в PostgreSQL;
- добавлен live dashboard, расширенный журнал транзита, CSV-экспорт и requestId для команд открытия;
- добавлены локальные smoke-тесты, mock-gateway и in-memory dev DB.

## Роли

### Арендатор

Основной экран показывает только доступные человеку проходы, въезды, выезды, двери, шлагбаумы и лифты. Для арендатора можно настроить:
- этажи;
- группы мест;
- парковочные места;
- предпочтительные маршруты;
- доступные участки.

На экране арендатора есть быстрые действия, фильтрация по маршруту и кнопка "Позвонить диспетчеру". Номер диспетчера задается переменной:

```bash
DISPATCHER_PHONE=+7 936 004-67-42
```

### Диспетчер

Диспетчер может работать с оперативным экраном и журналом событий в рамках выданных прав. Роль рассчитана на сценарии:
- удаленно открыть нужный узел;
- увидеть последние события;
- понять, кто отправил команду;
- отследить ошибку открытия.

### Администратор паркинга

Администратор управляет людьми и структурой доступа:
- создает арендаторов, диспетчеров и администраторов;
- назначает участки;
- задает этажи, группы мест, места и маршруты арендатора;
- сбрасывает пароли;
- смотрит журналы в рамках доступных прав.

Обычный администратор может быть ограничен по `assignable_zones`, чтобы не управлять чужими участками.

### Системный администратор

Системный администратор управляет технической частью:
- устройства;
- участки;
- gateway-настройки;
- аудит;
- роли администраторов;
- полный набор участков.

## Выдача доступа новым пользователям

При создании пользователя администратор может указать пароль вручную или оставить поле пустым.

Если поле пустое:
- система генерирует временный пароль;
- в базе сохраняется только хеш;
- пароль показывается администратору один раз после создания;
- если указан email, письмо отправляется пользователю.

По умолчанию письмо не содержит пароль. Это сделано специально: `MAIL_INCLUDE_PASSWORD=false`. Пользователь получает логин и инструкцию получить пароль у администратора. Если бизнес-процесс требует отправлять пароль в письме, нужно явно включить:

```bash
MAIL_INCLUDE_PASSWORD=true

Начиная с текущей версии это допускается только вне production. Если `NODE_ENV=production`, приложение завершит запуск с ошибкой.
```

При сбросе пароля новый временный пароль также показывается администратору один раз.

## Что важно при разворачивании вместо архивной версии

Перед заменой версии на сервере:
- сделать бэкап PostgreSQL;
- сохранить текущие переменные окружения;
- добавить `DISPATCHER_PHONE`;
- проверить `SESSION_SECRET`, `DATABASE_URL`/`PG_URL`, `APP_BASE_URL`, `GATEWAY_BASE_URL`, `GATEWAY_KEY`;
- не копировать на сервер локальные папки `node_modules`, `data`, `public/data` и реальный `devices.json` с IP/логинами устройств;
- поставить зависимости через `npm ci`;
- запустить `npm start`.

Если таблица `devices` на сервере уже заполнена, приложение не перезатирает устройства из файла. Если таблица пустая и `devices.json` отсутствует, будут созданы безопасные тестовые устройства. Реальный импорт устройств лучше делать из админки или отдельным защищенным файлом на сервере.

Схема базы обновляется автоматически через `ensureSchema()`: добавляются недостающие колонки и индексы. Это рассчитано на обновление поверх старой версии, но бэкап перед первым запуском обязателен.

Аварийный file-fallback для журнала транзита теперь управляется явно через `ALLOW_FILE_TRANSIT_FALLBACK`. Для production рекомендуем оставлять `false`, чтобы не было "двойной правды" между БД и локальным JSONL-файлом.

После запуска проверить:
- `/health`;
- вход администратора;
- создание тестового арендатора;
- выдачу временного пароля;
- открытие одного устройства;
- журнал транзита;
- экспорт CSV.

## Проверка локально

Для полной локальной проверки без PostgreSQL:

```bash
GATEWAY_KEY=dev-gateway-key node scripts/mock-gateway.js
DEV_MEMORY_DB=true SESSION_SECRET=replace-with-secret ADMIN_PHONE=79000000000 ADMIN_PIN=RuntimeAdmin1234 GATEWAY_BASE_URL=http://127.0.0.1:9090 GATEWAY_KEY=dev-gateway-key PORT=18080 node server.js
SMOKE_BASE_URL=http://127.0.0.1:18080 npm run smoke:runtime
```
