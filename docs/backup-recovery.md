# Регламент резервного копирования и восстановления

## 1. Что подлежит резервному копированию

Обязательно:

- PostgreSQL database;
- production env-переменные в защищённом хранилище;
- перечень устройств, зон, пользователей и ролей;
- gateway-конфигурация;
- документы передачи и инвентаризации.

Не нужно бэкапить как источник истины:

- `node_modules`;
- `.git` на сервере;
- локальные временные файлы;
- runtime-cache;
- файлы, которые восстанавливаются из Git.

## 2. Периодичность

Рекомендуемый минимум:

- ежедневный автоматический backup БД;
- backup перед каждой production-выкладкой;
- еженедельная проверка восстановления на отдельной среде;
- немедленный backup перед массовой ротацией доступов или изменением схемы БД.

## 3. Создание backup

```bash
DATABASE_URL=postgresql://... BACKUP_DIR=/secure/backups npm run db:backup
```

Скрипт создаёт файл `moyaparkovka-<timestamp>.dump` и SHA-256 checksum рядом с ним.

## 4. Хранение backup

Backup должен храниться:

- вне публичной директории;
- вне репозитория;
- в доступе минимум у двух назначенных представителей Заказчика;
- с ограничением доступа по ролям;
- с контролем срока хранения.

Рекомендуемый срок хранения:

- ежедневные backup: 14-30 дней;
- еженедельные backup: 2-3 месяца;
- backup перед релизом: до подтверждения стабильности релиза.

## 5. Восстановление

Восстановление выполняется только после явного подтверждения:

```bash
CONFIRM_RESTORE=YES DATABASE_URL=postgresql://... npm run db:restore -- /secure/backups/moyaparkovka-YYYYMMDDTHHMMSSZ.dump
```

После восстановления:

1. Проверить `/health`.
2. Проверить вход администратора.
3. Проверить список пользователей, зон и устройств.
4. Проверить открытие устройства через gateway.
5. Проверить журналы.
6. Зафиксировать результат восстановления.

## 6. Действия при отказе сервера

1. Зафиксировать время отказа и симптомы.
2. Проверить платформу/VM/container status.
3. Проверить доступность PostgreSQL.
4. Проверить `/health`.
5. При необходимости поднять приложение на новой среде из Git.
6. Подключить актуальную БД или восстановить backup.
7. Проверить DNS/SSL.
8. Зафиксировать инцидент и принятые действия.

## 7. Действия при компрометации доступа

1. Немедленно отозвать/сменить скомпрометированный доступ.
2. Сменить `SESSION_SECRET`, если есть риск компрометации сессий.
3. Сменить `GATEWAY_KEY`.
4. Сменить `ADMIN_PIN`/админские пароли.
5. Ротировать `DEVICE_SECRET_ENCRYPTION_KEY` только по отдельному плану миграции секретов устройств.
6. Проверить audit и transit logs.
7. Зафиксировать инцидент и уведомить ответственных.
