# Регламенты эксплуатации

## 1. Регламент резервного копирования

### Что бэкапится

- PostgreSQL database.
- Production env-переменные в защищённом хранилище.
- Реестр устройств, зон, gateway и сервисных доступов.
- Документы инвентаризации и передачи.

### Как часто

- Ежедневно автоматически.
- Перед каждым production-релизом.
- Перед массовой ротацией доступов.

### Где хранится

- В защищённом хранилище Заказчика.
- Не в Git.
- Не в `public`.
- Не на единственном сервере приложения.

### Кто отвечает

Назначается минимум два ответственных представителя Заказчика:

| Роль | ФИО | Контакт | Обязанность |
|---|---|---|---|
| Владелец backup | TBD | TBD | Контроль создания и хранения |
| Замещающий | TBD | TBD | Проверка восстановления |

### Как проверяется восстановление

- Не реже одного раза в неделю на отдельной среде.
- После каждого восстановления фиксируются дата, backup-файл, результат `/health`, проверка входа и журналов.

## 2. Регламент обновлений

### Подготовка

- Изменение создаётся в отдельной ветке.
- Проверяется локально.
- Документация обновляется вместе с кодом.
- Секреты не коммитятся.

### Тестирование

Минимум:

```bash
npm install
npm run smoke:runtime
npm run ops:inventory
```

### Согласование

Перед production-выкладкой Заказчику передаются:

- краткое описание изменений;
- список затронутых файлов;
- риски;
- план отката;
- подтверждение наличия backup.

### Выкладка

- Только из Git.
- Только согласованная ветка/tag.
- После выкладки проверяются `/health`, login, dashboard, gateway open, logs, audit.

### Откат

- Через предыдущий deployment или Git tag.
- При необходимости через restore БД.
- Результат отката фиксируется письменно.

## 3. Регламент управления доступами

### Категории доступов

- Репозиторий.
- Production platform / Yandex Cloud / Railway.
- VM/server/container users.
- PostgreSQL.
- Domain/DNS/SSL.
- SMTP/mailbox.
- Gateway/controllers API.
- Superadmin в приложении.
- Service accounts.

### Кто распоряжается

Критичные доступы должны находиться под контролем Заказчика. Единоличное владение Исполнителем недопустимо.

### Ротация

Ротация выполняется:

- после передачи контроля;
- при смене подрядчика/сотрудника;
- при подозрении на компрометацию;
- планово не реже одного раза в 90 дней для критичных ключей.

### Передача новых доступов

- Передача фиксируется в реестре.
- Секреты передаются защищённым каналом.
- Нельзя пересылать действующие пароли/PIN по обычной email-переписке.
- После первичного входа пароль должен быть изменён владельцем.

### Исключение единоличного владения

Для каждого критичного доступа указывается минимум два владельца со стороны Заказчика. Если платформа поддерживает роли, используются индивидуальные аккаунты, а не общий логин.
